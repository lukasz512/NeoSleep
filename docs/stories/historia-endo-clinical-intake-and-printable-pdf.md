## Refined User Story: Historia Endo — Structured Clinical Intake Capture + Pre-filled Printable PDF

**Classification**: feature
**Raw input**: A partner dentist (Lorena González, via WhatsApp) asked that the "Historia Endo" (endodontics) clinical intake form become interactive: the patient's medical-history section should be a yes/no checklist instead of free text ("La parte de antecedentes médicos para que el solo responda si, si o no padece de algunas de estas enfermedades u otras"), and a second section should let the dentist mark yes/no findings from the oral exam — Bruxismo, Paladar estrecho, Lengua geográfica, Xerostomia, Clase esqueletal I/II/III, Respirador bucal, Ausencias dentales, Enfermedad periodontal, Evaluación del ATM. Separately, Łukasz added: the document also needs to be **printable**, and should auto-pull whatever patient/doctor data NeoSleep's system already has, leaving the rest blank for manual completion during the visit. Two reference images were also shared alongside the "HISTORIA ENDO (2).pdf" source document: a STOP-Bang OSA screening questionnaire (8 yes/no items, each worth 1 point) and an OSA-consequences reference table (cardiovascular/metabolic/neurocognitive/neoplastic effects) that reads as patient-education content, not a data-capture form. This story is deliberately sequenced after the Documents-system architecture (Slice 1 of `docs/stories/documents-system-entity-integration.md`, already shipped), which this feature is expected to build on.

### As a partner dentist (HCP), I want to record a patient's medical history and oral exam findings as quick yes/no taps instead of handwriting them, and print a pre-filled Historia Endo form for the patient's chart, so that intake is faster, more legible, and I'm not re-writing information NeoSleep already has on file.

### Stakeholder Notes
- 👤 User: The dentist's job here is "capture intake data fast, during a real patient visit, without re-typing what's already known." Today this is 100% paper — free-text medical-history boxes and a hand-drawn odontogram, per the source PDF. The ask is narrowly scoped to two checklists (patient antecedentes médicos, dentist oral-exam findings) plus a printable, pre-filled output — not a full digitization of every field on the 3-page PDF (pain history, radiographic findings, odontogram, diagnosis/prognosis/treatment, evolution notes are all still free-text/manual in the source and were not called out by Lorena or Łukasz as needing structured capture).
- 🏢 Client: A tenant whose HCPs do chairside intake gets a faster, more legible, more complete record — directly reduces the "illegible handwriting / incomplete form" failure mode a paper intake has today. Real ROI for a dental-focused tenant, though NeoSleep's current tenant roster is sleep-appliance-focused (NeoSleep) — worth confirming this is for NeoSleep's own dental partners specifically, not a generic pattern being requested speculatively.
- 🩺 Patient: **Direct patient-safety relevance**, not indirect — this is literal clinical intake data (allergies, current medications, pregnancy status, cardiac/renal conditions, anticoagulant-relevant history) that informs a procedure (root canal treatment/retreatment) with a documented informed-consent process. Data-entry errors or an incomplete pre-fill here have real clinical stakes, unlike most of this platform's rep-facing CRM data.
- 🚀 NeoCRM/Platform: Reusable pattern if built generically (a "structured clinical checklist + pre-filled printable PDF" mechanism could serve other intake forms beyond dental — same shape as `sleep_study`'s existing structured-capture pattern). Risk: if built as a one-off "endo_intake" table with hardcoded questions, it doesn't generalize to a future tenant's own different intake form. Flag for `/ceo`/`/product`: is this worth generalizing now (a config-driven checklist definition, closer to the document-editor's own "templates are data, not code" philosophy) or is a hardcoded v1 acceptable given only one dental partner has asked for this so far?
- ⚖️ Compliance: Real flag, same category as the platform's other consent/clinical documents. This intake form ends in a **root-canal informed-consent text block with patient+doctor signatures** (page 2 of the source PDF) — that consent text should go through the same versioned `document_content_version` pipeline as the platform's other consent documents (`docs/stories/document-content-editor.md`), not be hardcoded into a static template, and any captured medical-history data (allergies, pregnancy, HIV, cardiac conditions) is GDPR Art. 9 special-category health data requiring the same encryption/access-control posture already applied to `patient.diagnosis_code`/`medical_record`. `/legal` input recommended on retention and on whether the signature capture here is in-scope now or deferred like the platform's other signature flows.

### Medical-Industry Trend Check
- The American Dental Association (2017 policy) and the American Academy of Dental Sleep Medicine's screening standards establish that dentists are expected to screen patients for OSA risk (STOP-Bang or equivalent) and refer to a physician for diagnosis — screening tools are used "either digitally or in paper form," and digital intake platforms (e.g. Somnoware) already support this as a standard workflow, not a novel one. ([AADSM Dental Sleep Medicine Standards](https://aadsm.org/journal/special_article_1_issue_53.php))
- Referral **compliance** after a positive dental OSA screen is a known weak point in this exact workflow — one study found only 18.3% of at-risk patients (20.4% of those screened) followed through on a referral, with "dentist recommendation" as a top compliance factor. ([PubMed: Facilitators and barriers to referral compliance](https://pubmed.ncbi.nlm.nih.gov/28984173/)) This is directly relevant to whether STOP-Bang capture (question below) should be scoped into this feature: NeoSleep's own business model depends on dentist-initiated OSA referrals converting, so a digitally-captured, chart-linked STOP-Bang score (rather than a loose paper form) is a plausible lever on exactly the compliance gap this research identifies — worth flagging to `/product`/`/ceo` as a reason to *not* treat STOP-Bang as out-of-scope by default.

### Acceptance Criteria (testable) — ALL DONE (2026-09-16), see Hand-off for what's still manual
- [x] Patient antecedentes médicos: each condition listed in the source PDF (Anemia, Diabetes, Tabaquismo, Endocrinos, Sinusitis, Alcholismo, Hipertension arterial, Hepatitis, Cancer, Adicciónes, Problemas cardiacos, Problemas renales, VIH, Neurologicos, + free-text "Otros") is a discrete yes/no capture, not a free-text box.
- [x] Dentist oral-exam findings: Bruxismo, Paladar estrecho, Lengua geográfica, Xerostomia, Clase esqueletal (I/II/III — not binary, a 3-way choice), Respirador bucal, Ausencias dentales, Enfermedad periodontal, Evaluación del ATM are each a discrete yes/no (or, for Clase esqueletal, a 3-way) capture.
- [x] Captured responses are stored per patient — resolved to one record per patient (see Repeat visits question below).
- [x] A printable PDF is generated that pre-fills, from existing system data: patient name, and (via the `patient.practitioner_id` link) treating doctor name and clinic/organization name — implemented via a new `dataFields` option on `renderHtmlToPdf` (see the deviation note below) and the existing `document_content_version` pipeline.
- [x] Fields NeoSleep's system does not have (pain history, radiographic findings, odontogram markup, diagnosis/prognosis/treatment plan, vital signs) render as **blank, fillable-on-paper** sections on the printed PDF.
- [x] The root-canal informed-consent text block is sourced from the versioned `document_content_version`/`DOCUMENT_MANIFEST` pipeline (new `historiaEndo` manifest entry, admin-editable via the Slice-1 Permissions tab) — not hardcoded.
- [x] The generated PDF's `file_attachment` row (`entity_type="patient"`) is discoverable from the patient's own "Documents" tab — reuses Slice 1's `GetPatientDocumentsQuery` with zero extra frontend work, confirmed.

**Deviation from the original AC wording, found during implementation**: `informedConsent.html`'s own doc comment described `data-field` filling as happening via a real Puppeteer `page.evaluate()` inside `apps/api`, but nothing in the codebase actually implemented that step (confirmed: `renderHtmlToPdf` took only a plain HTML string, no hook to run code inside the live page). Rather than build a string-replace workaround in the DB-free `packages/documents` package (less safe — the original design's own stated reason for using `page.evaluate()` + `textContent` was auto-escaping), `renderHtmlToPdf` gained a new `dataFields?: Record<string,string>` option that fills matching `[data-field="key"]` elements via `page.evaluate()` internally, keeping Puppeteer fully encapsulated (this file's own header comment forbids callers touching Puppeteer directly) — this is the first real implementation of what the templates' comments always described, not a new pattern.

### Open Questions — RESOLVED (answers from Łukasz, 2026-09-16), one still blocking
- [x] **Hardcode vs. generalize**: hardcoded v1 — only one dental partner (Lorena's clinic) has asked for this so far; a config-driven checklist is a later generalization if/when a second tenant needs a different question set.
- [x] **STOP-Bang scope**: **in scope**, rides in this same story — accepted over the "defer" recommendation, given the referral-compliance angle from the trend check above.
- [x] **Signature/consent capture**: deferred, same as the platform's other signature flows. v1 is filled data + a printable PDF for a handwritten signature on paper, matching the source PDF's own "Firma Paciente / Firma Doctor" boxes.
- [x] **Repeat visits / per-tooth**: resolved by Łukasz (2026-09-16) — **one record per patient**, edited over time. If a real per-tooth/per-treatment need surfaces later, that's an additive change (a second table or a `tooth` field), not a rework of this one. `DIENTE` (tooth) from the source PDF becomes an optional field on the single per-patient record, not a uniqueness key.

### STOP-Bang addition (now in scope) — DONE, architecture per ADR-022
- [x] 8 yes/no items (Snoring, Tiredness, Observed Apnea, Pressure, BMI>35, Age>50, Neck circumference>40cm, Gender=male), each worth 1 point, with a computed total score captured alongside the answers via a Postgres `GENERATED ALWAYS ... STORED` column — verified computed by Postgres itself in `db/stopBangScreening.spec.ts`, never recomputed in application code.
- [x] **Data-model decision** ([ADR-022](../ADR-022-endo-intake-and-stop-bang-schema.md)): its own table, `stop_bang_screening` — multiple rows per patient (it's a recurring screening, not a one-time intake), not embedded on `endo_intake` and not added to `sleep_study` (whose `status` column is a device-study state machine, a different lifecycle). `pressure` is its own captured boolean, deliberately not derived from `endo_intake.has_hypertension`.
- [x] Same pre-filled-printable-PDF treatment as the Historia Endo checklist (patient/doctor/clinic pre-filled, score computed and shown, reused the same template mechanism — `templates/stopBang.html`).

### Other Open Questions
