## Refined User Story: linear-worker pipeline hardening — artifact/QA-checklist/1-click-run, hoisting check, conditional double-pass, push-preflight

**Classification**: feature
**Raw input**: Łukasz (2026-09-20, verbatim/translated from a dense multi-part Polish message): dissatisfied specifically with `linear-worker`'s output quality ("bardziej chodzi mi o linear, bo z niego jestem mniej zadowolony"), but wants the same conventions applied to interactive sessions too where it makes sense. Wants every ticket to produce 3 concrete things (ideally one consolidated, short artifact): a visual summary, a "1-click" way to spin up the dev environment, and a QA checklist to verify the story. Wants a conditional double-implementation-and-compare pass for architecturally ambiguous tickets. Wants an explicit, mandatory "is this platform-generic or tenant-specific — can it be hoisted?" check per ticket, given the white-label model. Wants a "backward consistency audit" step with test coverage as the key signal. Wants each artifact distilled to what's actually essential ("za dużo AI slop, za mało informacji"). Wants `linear-worker`'s known GitHub App push-access bug (403, unresolved since 2026-09-16) fixed as part of this same effort.

### As Łukasz, reviewing work that either a nightly worker or an interactive session produced on a Linear ticket, I want a small, consistent, visual completion package plus real safeguards on ambiguous/risky work, so that I can verify what changed and trust unattended work without reading a wall of text or re-deriving the diff myself

### Stakeholder Notes
- 👤 User: Łukasz is the sole consumer of this — he reviews tickets in Linear, often away from the terminal, and has explicitly said text-only summaries aren't enough ("AI slop"). The job here is making a finished ticket fast to *judge*, not just fast to produce.
- 🏢 Client: No direct effect — this is internal engineering process, invisible to any tenant. Indirect benefit only: more rigor before a change lands should mean fewer regressions reaching a tenant's reps.
- 🩺 Patient: No direct effect. `linear-worker` is already hard-blocked from touching `identities`/`patient`/`practitioner`/`consent`/`audit_log`/migrations/`auth.ts` unattended (Step 4 of its own procedure) — this story doesn't change that boundary. Indirectly, better pre-merge scrutiny lowers the chance of a defect eventually reaching a patient-adjacent flow.
- 🚀 NeoCRM/Platform: This *is* platform work — it's the engineering pipeline itself, not a tenant feature. The "hoisting check" item is explicitly about keeping the platform white-label-generic by default and only going tenant-specific on purpose, which is a direct platform-scalability concern.
- ⚖️ Compliance: No new flags — no schema, no PHI, no new data flow. Purely internal tooling/process.

### Acceptance Criteria
- [ ] A feature-classified ticket completed by `linear-worker` (or an interactive session) produces one consolidated Artifact — not three separate deliverables — with three clearly labeled sections: (1) visual summary of the change, (2) how to run it locally (references a `.vscode/tasks.json` task, not a hosted preview URL), (3) a manual QA checklist to verify the acceptance criteria.
- [ ] That Artifact is attached to the Linear ticket (`save_issue`'s `links`, matching the NEO-36 precedent) before the ticket can move to `Needs Review`.
- [ ] A `.vscode/tasks.json` task exists that runs `pnpm start` (Docker Postgres + API + PWA) as a single one-click/one-command action, and every completion Artifact's "run it locally" section names that task by its label.
- [ ] `linear-worker`'s procedure gains an explicit, mandatory line — stated during Step 5 (Enrich), before implementation — answering "is this change platform-generic or tenant-specific, and is hoisting to platform-level possible/desirable?" for every ticket, not just when it happens to come up.
- [ ] `linear-worker` gains a conditional double-implementation pass: only when `/arch` or `/product` flags a ticket as architecturally ambiguous (multiple reasonable approaches, no clearly-correct path) during Step 5, the worker implements it twice in two independent attempts and picks the more coherent one per an explicit rubric, recording both attempts' summaries in its completion comment.
- [ ] `linear-worker` gains a fail-fast git-push dry-run preflight (at Claim time or immediately before the real push) that detects a GitHub App 403 in seconds and moves the ticket to `Blocked` with an actionable comment, instead of discovering it only after a full implementation + self-check cycle (today's actual behavior — confirmed no such preflight exists yet, despite a stale memory claiming otherwise).
- [ ] The stale memory `project_linear_worker_github_app_access_broken.md` is corrected: NEO-25's actual merge (`917c745`) added a `DATABASE_URL`/environment preflight, not a GitHub-push preflight.
- [ ] Łukasz has visited https://github.com/apps/claude/installations/select_target and confirmed/granted push access for the org the worker's cloud sandbox runs under — this is a manual, out-of-band action; Claude cannot perform it, only detect via the new preflight whether it's still broken.
- [ ] A "backward consistency audit" step exists somewhere in the pipeline before a change is considered fully done — exact scope/cadence is an open question below, not decided yet.

### Open Questions
- [ ] **Double-pass mechanics**: does the worker self-adjudicate which of the two attempts is "more coherent" and land its own pick unattended (consistent with its existing Needs Review/Blocked-only terminal states — it can't literally pause overnight waiting for Łukasz), or should this only apply to interactive sessions where Łukasz is present to compare live? Recommend: worker self-adjudicates against an explicit rubric (test coverage, diff size/simplicity, CLAUDE.md convention adherence) and includes both attempts' summaries in the completion comment for after-the-fact review — but this is Łukasz's call since it's a real autonomy expansion.
- [ ] **Artifact template vs. bespoke design**: the `artifact-design` skill's own guidance explicitly warns against templated/cookie-cutter design, but "short, consistent, low-effort per ticket" pulls the other way. Does Łukasz want a genuinely reusable template (same shape every time, faster, less "craft") or a fresh design per feature (matches the skill's default, slower, more bespoke)?
- [ ] **Backward-consistency audit scope/cadence**: per-ticket (every single ticket gets a consistency+coverage audit, which is a real time cost for the worker's per-ticket budget) or a periodic/release-level gate wired to the existing `/audit` "release-gate" mode instead? His phrasing suggests end-of-pipeline-per-change, but that may be heavier than intended.
- [ ] **Confirm reading of the "Simsy"/"zaocznie" language** as describing the desired *feeling* once the concrete items above are delivered (effortless, more work landing unattended), not a literal separate gamification-UI build. Flagging rather than assuming.
- [ ] **Interactive-session parity**: `quality-gate.sh`'s Linear-artifact-marker check (built earlier this session) already fires for any feature-shaped diff regardless of who's driving. Should interactive sessions get the full "3 things" artifact + hoisting-check treatment too (recommended, low extra cost), while the double-pass stays worker-specific/optional (a human present doesn't need two full parallel runs)?
