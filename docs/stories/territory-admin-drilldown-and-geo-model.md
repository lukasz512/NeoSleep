## Refined User Story: Manual Territory Administration (Drill-Down) + Growth-Ready Geo Data Model

**Classification**: feature — new admin workflow (country-scoped, drill-down territory creation) plus an architecture decision (how territory data gets populated as the app scales: manual vs. auto-derived from postal code/geocoding, and how it stays Python-analytics-friendly).

**Raw input**: Łukasz, after the unified-territory-scope work landed: "terytoria nadal nie sa skonczone... chce recznie robic terytoria: w zakladzce terytoria admin i mnager moze dodawac terytoria dla tych krajow ktore widzi... kraj → prowincja (pobierz liste) → miasto (auto po wyborze prowincji, miasta wg wielkosci/stolica na górze) → dzielnica (np Polanco, jeśli da się łatwo pobrać). ...te regiony sa zalezne od lekarzy dostepnych, wiec chcialbym zeby to bylo calkiem dynamiczne... moznaby tworzac pacjenta/medico/hco automatycznie decydowac o regionie, np po kodzie pocztowym albo nazwach ulic? jak to sie robi w medical grade aplikacjach, jak aplikacja urosnie, zeby dalo sie latwo podlaczyc do pythona? dzielnica lepiej auto ladowane czy tworzone przez admina?" Wants this done on a **new branch**, planning-only in this session.

### As an admin/manager, I want to build out my country's territory tree through a guided drill-down (country → province → city → district) instead of a flat manual form, with cities and — where real data exists — districts pre-populated from an authoritative source, so that territory assignment is fast, consistent, and ready to drive HCP↔patient matching as more doctors get added.

### Stakeholder Notes
- 👤 User (admin/manager): Today's `TerritoriesView.vue` is a flat "name/code/kind/country_code/parent_id" form — functional but tedious and error-prone (nothing stops you from picking the wrong parent, or misspelling a city that already exists). A drill-down removes that class of mistake entirely and matches how they already think about the hierarchy (they'd never say "add a level-3 node," they'd say "add a colonia under Ciudad de México, Mexico").
- 🏢 Client: Territory quality directly feeds the two things a tenant actually cares about here — rep coverage reporting ("who covers what") and (once built) automatic HCP↔patient routing by proximity. Garbage-in territory data (typos, wrong parents, missing cities) quietly breaks both.
- 🩺 Patient: Direct downstream effect once HCP↔patient matching ships (explicitly named as the next feature) — a patient's assigned district is what will surface nearby doctors. Getting the district/city data right now is what makes that feature trustworthy later, not cosmetic.
- 🚀 NeoCRM/Platform: The country-scoped constraint (admin/manager only manage territories inside their own RBAC scope, migration 022) is a natural extension of work already shipped, not new plumbing — the drill-down just needs to read `getAllowedScopePaths` the same way Patient/HCP/HCO queries already do.
- ⚖️ Compliance: No new personal-data category — territory nodes are geography reference data, not patient data. The auto-derivation options below (postal code/geocoding) do touch patient/HCP/HCO *address* fields, which are already-classified personal data under existing GDPR/LFPDPPP handling — no new consent basis needed since address collection is already covered, but worth a one-line confirmation from `/legal` before building the auto-derivation path, not before the drill-down UI itself.

### Medical-Industry Trend Check
- **FHIR's `Location` resource** (the actual healthcare interoperability standard, HL7) models exactly this shape: a self-referencing `partOf` hierarchy (no fixed depth, no special-cased levels) plus optional WGS84 lat/long on any node. This *validates* the current `territory.parent_id` + `organization.latitude/longitude` design rather than suggesting a redesign — an eventual FHIR export/interop story would map onto it directly. [Location - FHIR R5](http://hl7.org/fhir/location.html)
- **Mexico already has a free, authoritative postal-code → colonia/municipio/estado dataset**: SEPOMEX (Correos de México), with several ready-to-use open-source mirrors/APIs. Given a postal code, it returns the *exact* colonia (district) list — this is the concrete answer to "can districts be auto-fetched for Mexico": yes, from day one, no geocoding API call needed. [SEPOMEX REST API](https://github.com/IcaliaLabs/sepomex), [API-Codigos-Postales](https://github.com/acrogenesis/API-Codigos-Postales), [mexpost](https://github.com/open-mexico/mexpost)
- **CRM territory-management practice (Salesforce/Dynamics/Zoho) uses both postal-code lookup and full geocoding**, and treats them as complementary, not competing: postal code for a fast, low-maintenance first assignment; geocoding (lat/lng) for precision once available. Neither replaces the other. [EasyTerritory postal lookup](https://www.easyterritory.com/documentation/dynamics-365-integration/postal-code-lookup-plugin/), [Maplytics territory guide](https://www.maplytics.com/blog/everything-you-need-to-know-about-crm-sales-territories-and-dynamics-365-maps-integration/)

### Architecture Recommendation (concrete, not just options)

1. **Country/Province — manual, admin-curated, rarely touched.** Already true today; no change. Small, stable lists (Mexico: 32 states; Poland: 16 województwa) — not worth automating.

2. **City — pre-loaded from a reference dataset per country, not fetched live per request.** Batch-import once per market (a seed/migration script, same shape as `002_seed.sql` already uses for the shallow 2-level PL/MX/TH seed), ordered by population so "capital/biggest first" is a stored sort key (`territory.metadata.population` or a dedicated `sort_rank` column), not a runtime computation.
   - **Mexico**: SEPOMEX/INEGI municipio list — already includes population-adjacent ordering data via INEGI's own catalogs.
   - **Poland**: the equivalent authoritative source is **TERYT** (GUS's national registry of territorial division units) — gmina/powiat/województwo, free, government-maintained, same "import once" shape as SEPOMEX.
   - This directly answers "auto-fetch cities after picking a province": yes, but from a **pre-imported local table**, not a live third-party API call on every admin click — cheaper, faster, works offline, and matches this codebase's existing convention of local reference tables (`lookup`, `territory` itself) over live external dependencies for stable data.

3. **District/neighborhood — auto-loaded for Mexico (SEPOMEX gives it for free), admin-created elsewhere.** Direct answer to "dzielnica auto ladowane czy admin?": **auto-load where a real free dataset exists (Mexico, via SEPOMEX/postal code), fall back to admin-created for markets that don't have one yet (Poland — postal codes there map to street ranges, not named neighborhoods; Thailand — TBD, research when that market activates).** Don't build a bespoke worldwide neighborhood dataset; don't force manual entry where free authoritative data already exists either. Import SEPOMEX's postal→colonia mapping as a one-time batch job (same pattern as #2), not a live per-request API dependency.

4. **Patient/HCP/HCO record creation — auto-suggest territory_id from postal code (primary) with existing geocoding as a fallback/precision layer, always admin/rep-editable, never silently authoritative.** Concretely:
   - On save, if `postal_code` is present, look it up against the imported SEPOMEX/TERYT table and set `territory_id` to the matching district/city node.
   - `services/geocoding.ts` already exists and is already used for `organization.latitude/longitude` — extend it to also request the locality/sublocality/postal component from the same geocode response, as a secondary signal when postal code is missing or ambiguous. This reuses infrastructure that's already built and already approved (no new external dependency).
   - Never lock the field — same principle as `organization.latitude/longitude` today (auto-set, but the address fields stay manually editable and re-geocode on change). Getting matched wrong should be a one-field fix for a rep, not a support ticket.
   - This is also the practical fix for "regions depend on which doctors actually exist there, want it dynamic": doctors/patients arriving with real addresses is what populates the tree's actual usage over time — the admin drill-down is for building the *reference* hierarchy, auto-assignment is what actually *populates* real records against it day to day.

5. **Data flow / scale / Python interop**: keep Postgres (with `ltree`) as the single source of truth — don't fork territory data into a separate analytics store prematurely. `ltree` paths serialize as plain dot-strings (`global.mx_id.cdmx_id.polanco_id`), which pandas/Python can consume directly via a straightforward read query (`SELECT id, name, kind, path::text FROM territory`) with zero custom serialization — this is already "Python-ready" as designed. When real analytics volume justifies it, the standard next step is a scheduled read-only export (or a Supabase read replica) feeding a warehouse — not a redesign of the territory model itself. The one-database-per-country future Łukasz mentioned is also already compatible: each country's subtree is self-contained under the shared Global root, so splitting later is a data copy, not a schema change.

### Acceptance Criteria
- [ ] Territories admin screen becomes a guided drill-down (Country → Province → City → District), each step's options scoped to (a) the parent just chosen and (b) the acting admin/manager's own RBAC territory scope (`getAllowedScopePaths`).
- [ ] City list is pre-imported reference data (SEPOMEX for MX, TERYT for PL), sorted by a stored importance/population rank, not fetched live per keystroke.
- [ ] District/neighborhood step auto-populates from the SEPOMEX postal-code dataset for Mexico; for markets without an equivalent free dataset, the step falls back to a manual "add new" affordance instead of blocking.
- [ ] Patient/HCP/HCO create/edit auto-suggests `territory_id` from `postal_code` (and/or existing geocoding) but leaves it editable; the resolved value is visibly shown as a suggestion, not silently applied without the rep seeing it.
- [ ] A new territory node created through the drill-down still gets a correct `path` (reuses `recomputeTerritorySubtreePath`, `db/territory.ts`) — no special-cased insert path.
- [ ] Real-DB integration tests per CLAUDE.md's no-mock rule, covering: country-scoped admin cannot create a node outside their scope; SEPOMEX import produces valid parent-linked rows; postal-code auto-suggestion resolves to the correct existing node.
