# Claude workflow rules — full text

Moved out of CLAUDE.md on 2026-10-03 (CORE-103): CLAUDE.md is loaded into every session, so it keeps one line per rule and points here. Text below is unchanged; hooks in `.claude/hooks/` enforce it.

## Git / PR Workflow
- Never push directly to `dev`, `prod`, or any shared branch — always branch, commit, `git push -u origin <branch>`, and give the user the GitHub "create a pull request" link GitHub prints after the push (`https://github.com/<org>/<repo>/pull/new/<branch>`).
- **The PR itself is always created by the user, never by Claude/CI tooling on their behalf** — this holds even if `gh` is authenticated; review happens before a PR exists, not just before merge.
  - **One exception (Łukasz, 2026-09-25): Renovate** (`renovate.json`) opens dependency-upgrade PRs into `dev` by itself — one grouped minor/patch PR a week, majors only after a tick in its Dependency Dashboard issue, security fixes immediately. It never merges anything (`automerge: false`); merging stays Łukasz's call.
- This repo enforces the above with a GitHub ruleset that rejects direct pushes (`GH013: Repository rule violations — Changes must be made through a pull request`) — expect this on `git push` and don't try to route around it (no force-push, no branch-name workaround).
- This is an interim policy, not the final CI/CD design — a fuller flow (environments, required checks, promotion) is still to be worked out.

### Ticket traceability
- **The work board is the one source of truth (CORE-187, decision D2, 2026-10-07).** Tickets live on `/platform/board` (platform schema); Claude sessions use `pnpm board` (`infrastructure/scripts/board.mjs`) with a per-device session token issued on the board (Session tokens) and stored in `.claude/local/board.json`. A session ticket lands in Building with the `session` label; a session can comment, link, set the branch and move to Needs Review, never Done. Linear is read-only (`.claude/hooks/pre-tool-linear-readonly.sh` denies every write) for 30 days, then a full local export and the workspace is closed (≈ 2026-11-07). Wherever the history below says "Linear", read "the board".
- **Every change gets a Linear ticket before its worktree/branch — trivial ones included (Łukasz, 2026-09-26, NEO-84).** The ticket is short and only about its change: `## Problem` (1-3 sentences) / `## Change` (bullets) / `## Done when` (checkable bullets), max 1500 characters. Enforced: `pnpm board create` and the board API reject a new session ticket in any other shape; `quality-gate.sh` blocks a changed branch with no `<key>-<n>` in its name.
- **Two teams (Łukasz, 2026-09-28, CORE-23; board teams since CORE-187).** **CORE** (NeoCRM CORE) = the platform: anything every tenant gets (engine, notifications, calendar, RBAC, tooling, infra, dependency upgrades). **NEO** (NeoSleep) = client-specific work only (OrthoApnea, Estudios, Historia Clínica, NeoSleep content/branding, their requests). Pick the team when creating a ticket; if unsure, CORE. Branches lead with the ticket ID of either team (`core-23-team-split`, `neo-163-…`). Allowed keys live in `.claude/ticket-teams` — a new client team (e.g. AJM, 4Seasons, same repo) is one line there. Moved tickets keep working under their old `NEO-<n>` link.
- Name the worktree/branch so the Linear ticket ID leads: `EnterWorktree(name: "<ticket-id>-<kebab-slug>")` (e.g. `eng-123-territory-admin-crud`). `EnterWorktree` prefixes `worktree-`, so the ID stays visible in the resulting branch (`worktree-eng-123-territory-admin-crud`) — this mirrors the nightly worker's own `worker/<ticket-id>-<slug>` pattern (`.claude/skills/linear-worker/SKILL.md`), same "ticket ID always leads" rule for human-initiated and automated work alike.
- As soon as that worktree/branch exists, comment on the Linear ticket with the branch name so the ticket shows "work started, on branch X" before any PR exists — do this before implementation starts, not as an afterthought.
- When handing the user the PR link after a push, prefer a pre-filled compare URL over the bare one GitHub prints — `https://github.com/<org>/<repo>/compare/dev...<branch>?quick_pull=1&title=<encoded-title>&body=<encoded-body>` — with the Linear ticket ID/title in `title` and a plain `NEO-<n>` reference (or a full Linear link) in `body`, so Linear can auto-link on merge if its GitHub integration is connected. **Never use `Fixes`/`Closes`/`Resolves <TICKET-ID>`** — see the 2026-09-20 correction below. This still only pre-fills GitHub's form; the user clicks "Create" themselves, same as always.
- Confirmed 2026-09-16: Linear's GitHub integration is connected for this repo/org — a branch name containing the ticket ID auto-links to the ticket, and a PR title/body with `Fixes <TICKET-ID>` (or `Closes`/`Resolves`) auto-transitions the ticket to Done on merge.
  **Correction, 2026-09-20**: that auto-close is exactly what Łukasz does *not* want — closing a ticket is a decision he wants to make himself, not a side effect of a PR merging (NEO-36/NEO-39 got silently auto-closed by PR #129's `Fixes` line and had to be manually reopened to `Needs Review`). Expectation, not yet independently verified on this repo: a plain ticket reference (`NEO-<n>` with no `Fixes`/`Closes`/`Resolves` in front of it) still creates the link/attachment when the PR merges, just without the status transition — this is standard Linear GitHub-integration behavior, but watch the next PR's ticket(s) to confirm it holds here too. Use plain references from now on, in PR bodies and anywhere else a ticket ID is cited (`linear-worker`'s own Step 9 already never used the magic-word form, so no change needed there).
- **Session title leads with the ticket ID too.** Claude Code auto-generates each session's title (shown in the VSCode sidebar) from the conversation itself — there is no tool to set it directly, only the user-run `/rename` command. `pnpm board create` prints a reminder with the new ticket ID (it replaced the Linear `PostToolUse` hook in CORE-187) so Łukasz can run `/rename` and Claude picks it up as `[<TICKET-ID>]` in its own replies. When the ticket ID is known before the session starts instead, just open the first message with `[<TICKET-ID>] ...` directly.
- Full rationale: `docs/stories/linear-task-traceability.md`.

### Standing decisions (Łukasz, 2026-09-24) — enforced by hooks
- **Every new thread runs in its own worktree — never ask.** Before the first file edit, call `EnterWorktree` (`<ticket-id>-<kebab-slug>` with a ticket, otherwise `<kebab-slug>`). Pure questions/research with no edits need none. Enforced by `.claude/hooks/session-start-worktree-check.sh` (instruction) + `.claude/hooks/pre-tool-main-tree-guard.sh` (PreToolUse, denies Edit/Write on main-tree files; `.claude/worktrees/` and `.claude/local/` stay writable).
- **Every change ships with a published Artifact — always, ticket or not, trivial or not.** Sections: What changed / Run it locally / Verify it; any UI change (`.vue`/`.css`/`.scss`) also needs a real before/after (screenshots of the running app, or a clearly labeled mockup when no live render is possible). Give Łukasz the link in the reply. Once the branch is pushed, the **top** of the Artifact carries a "Create PR" button, the pre-filled compare URL described above (he still clicks Create on GitHub himself). Record it in `.claude/local/artifacts/<TICKET-ID>.json`, with `prUrl` once pushed. Enforced by `.claude/hooks/quality-gate.sh`, which checks the whole branch vs `origin/dev` — committing before the turn ends does not skip it.
- **Build it with `/ship-artifact` (Łukasz, 2026-09-25).** The Artifact is the one deliverable he reads after a session, so it always has the same shape: one template (`.claude/skills/ship-artifact/`), Claude writes only the summary, decisions, before/after (backend → behavior table, UI → real screenshots) and verify list; the script fills links, PR URL and marker. Ticket branches: link it on the board ticket + post the summary comment (`pnpm board link` / `pnpm board comment`; hook-enforced: `boardLinked`/`boardCommented` in the marker, older markers' `linear*` fields still count), then move the ticket to **Needs Review** once pushed — never Done.
- **3 links, one index (Łukasz, 2026-09-26, NEO-84).** Every Artifact and its ticket comment carry the same 3 links: Artifact (claude.ai), board card (`/platform/board?item=<KEY>`), VS Code session (`vscode://anthropic.claude-code/open?session=<id>`), plus the PR button. Every shipped change also gets one line in the shared **NeoSleep Change Index** Artifact (ticket, status, 1 sentence, links; URL in `.claude/local/artifact-index-url.txt`). Texts are capped by `build.mjs` (headline 110 chars, summary 2 sentences) — cut, don't pad. Hook-enforced (`boardUrl` or older `linearUrl`, `vscodeUrl`, `indexed` in the marker).
- **Merged worktrees and branches are removed automatically (Łukasz, 2026-09-26, NEO-84).** Every session start runs `worktree-clean.sh --auto` in the background: it removes worktrees, local branches and origin branches whose commits are all on `origin/dev` (ancestry or identical patch), copying Artifact markers to the main checkout first. Unmerged, dirty, locked (open session) and `backup/*` are only listed (`pnpm worktree:clean`) for Łukasz to decide. Claude may run `pnpm worktree:clean` (allowed in settings); never raw `git branch -D`.
- **The "Create PR" link must be mergeable (Łukasz, 2026-09-25).** Once the branch is pushed, the same hook fetches `origin/dev` and trial-merges it in memory (`git merge-tree`); conflicts block the turn and list the files. Merge `origin/dev` into the branch, resolve, re-test, push, refresh the Artifact — only then hand over the link.
- **After the merge, verify on pwa-dev (Łukasz, 2026-09-25).** When the branch's HEAD is in `origin/dev`, the same hook blocks until the Artifact marker has `devVerified {sha, ok, at, summary}` for that HEAD. Wait for the dev "Deploy NeoSleepCare App" run containing it to go green, run `node infrastructure/scripts/smoke-dev-bundle.mjs --markers <marker>` (the change's `smokeMarkers`: strings only the new code contains), then `node infrastructure/scripts/smoke-dev-ui.mjs --check "<route>=<selector>" …` — a logged-in click-through of the changed screens (desktop + phone, fails on page errors / 5xx / missing selectors) with the QA account `qa-smoke@neosleepcare.com` whose credentials live only in `.claude/local/qa-dev.json` (create/rotate with `pnpm --filter @neo/api seed:qa-user -- --out ../../.claude/local/qa-dev.json`; the password is never put in Render, GitHub or the repo) — record the result, and tell Łukasz.
- **Questions arrive as a form (2026-09-26, NEO-88).** 2+ questions or decisions for Łukasz → `/decision-form` Artifact (options per question, recommendation marked, notes field, "Send to Claude"), never a chat list. His answers come back as an artifact comment starting with `[decision-form]` that wakes the watching session. Injected by `.claude/hooks/prompt-submit-rules.sh` (once per session since CORE-103).
- **CI must be green before the PR link, and a red CI gets fixed by the same rules everywhere (Łukasz, 2026-09-28, NEO-182).** The rules live in one file, `.claude/ci-autofix.json`: max 2 fix attempts per branch, fixes limited to making the failing tests pass, then stop and escalate. The session, the GitHub handoff and the nightly worker all read it. Change the rules there, not in the readers. How each one applies it:
  - **Session:** `quality-gate.sh` waits for CI on the pushed HEAD, verdict from `infrastructure/scripts/ci-status.mjs`.
  - **Pre-push:** runs the harness e2e specs related to a `.vue`/`.css` change (`infrastructure/scripts/related-e2e.mjs`).
  - **GitHub:** `.github/workflows/ci-failure-handoff.yml` comments the failing tests on the PR and the Linear ticket, and re-queues the ticket for `linear-worker` with the `ci-failed` label.
  - **Worker:** fixes it in its CI-fix mode.
- **Routine non-UI tickets go to the worker: label `auto` (Łukasz, 2026-10-07, CORE-183).** Why: in the interactive session every reply re-sends the whole history, CI waits and handover steps included, which is the most expensive way to ship a backend fix. Put `auto` on a ticket when its change is backend logic, a hook, a script, config or docs, and its `## Done when` is precise enough to be the spec. Leave it off for anything with UI, a view, an API route, a migration, a product decision, or compliance-sensitive code (the worker's scope check refuses those anyway). Like every worker card it still needs your approval (board status `approved`, CORE-187); the label only changes what the worker does with it: `infrastructure/scripts/worker-auto.mjs pick` takes `approved` cards FIFO, one per run, and an `auto` card ends with the light handover (board comment + PR link, `needs_review`) instead of an Artifact page. If the diff turns out to touch UI anyway (`worker-auto.mjs guard`, same rule as `.claude/hooks/lib/change-shape.sh`), it pushes nothing and leaves a `Blocked:` comment with the card in `building`; the agent can't change labels, so you drop `auto` and take it to a chat session.
- **Short replies (2026-09-25).** The final message of a turn is only what needs Łukasz: the outcome in ≤2 sentences, plus any decision, risk, failure or link he must act on. Test counts, file lists and process go in the Artifact, which also opens with a 2-sentence summary and a "Needs your decision" box. Injected by `.claude/hooks/prompt-submit-rules.sh`, once per session since CORE-103 (prompt-time on purpose: a Stop hook can't shorten a reply already shown, only add a second one).

## Git tags — milestones
Use `git tag v<name>` to mark stable states before big changes:
```bash
git tag v1.0-rep-mvp       # milestone snapshot
git tag v0.9-before-rename # before a large refactor
git push origin --tags     # share tags with the team
```
Tags are immutable — always point to the same commit. Use `git checkout <tag>` to return to any point.
